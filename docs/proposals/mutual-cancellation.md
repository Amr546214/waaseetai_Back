# «الإلغاء بالتراضي» (mutual cancellation) — approved policy and implementation

Status: implemented locally (BE + FE). Migration `20261105120000_contract_cancellation_requests` is additive and was AMENDED in place (it has not been applied anywhere); rehearsed only on a local database, NOT executed on dev/prod. USD only.

## Approved policy (owner decision, 2026-11-05)
1. Before both parties agree: a client approving a stage pays that stage to the provider exactly as today; anything already paid stays.
2. After both agree the request becomes `AGREED_PENDING_SETTLEMENT` («تم الاتفاق — بانتظار التسوية»). Approving NEW stages and releasing their payments STOPS, enforced on the server: `reviewDelivery(approve)` answers 423 `CONTRACT_CANCELLATION_AGREED` (same pattern as the dispute freeze 423); amendments can no longer be applied. Delivery uploads, chat and revision requests stay open (they move no money). The agreement alone moves NO money.
3. Admin settlement screen (`/supper-admin-overview/cancellation-requests/:id`): stages already paid, unapproved stages, the REAL remaining escrow (`heldEscrowAmount`: price - released, as resolve-financial). An admin holding `disputes.resolve` + `payouts.send` (acting-role guarded, like `resolve-financial`) sets the provider's GROSS share of the remainder, sees the client's refund (= remainder - share) before confirming, and records the reason (10-2000 chars).
4. On confirm (`POST /api/admin/cancellation-requests/:id/settle`): ONE transaction executes the settlement and closes the engagement. Same mechanics as the financial dispute decision: contract row lock, `expectedHeldAmount` must equal the live remainder, refund + provider share = remainder, commission on the gross release with the cumulative `splitRelease` and the escrow's rate snapshot, escrow RELEASED (share > 0) or REFUNDED (share = 0), refund credited to the client wallet as `REFUND` with the unique reference `CANCEL-REFUND-<requestId>`, audit row `CANCELLATION_SETTLED`. Contract -> CANCELLED; project -> COMPLETED (share > 0) or DISPUTED (share = 0) and the client request COMPLETED/CANCELLED, mirroring resolve-financial (there is no CANCELLED project status). Any failure rolls everything back and the request stays `AGREED_PENDING_SETTLEMENT`. A repeated confirm returns the stored result (`replayed`), two concurrent confirms settle once (lock + conditional claim + unique refund reference). An open dispute refuses the settlement (423); a financial dispute decision and the settlement serialise on the same contract lock, whichever commits second is refused (409).

## API
client `GET|POST /api/client/projects/:projectId/cancellation-requests`, `POST /api/client/projects/cancellation-requests/:id/{respond,withdraw}`; provider `GET|POST /api/provider/projects/:projectId/cancellation-requests`, `POST /api/provider/cancellation-requests/:id/{respond,withdraw}`; admin `GET /api/admin/cancellation-requests[/:id]` (`disputes.view`) and `POST /api/admin/cancellation-requests/:id/settle` (`disputes.resolve` + `payouts.send`). The project workspace carries `cancellationFreeze {frozen, reason}` and `canApproveStage` accounts for it.

## Tables
`contract_cancellation_requests`: status `PENDING_OTHER_PARTY | AGREED_PENDING_SETTLEMENT | SETTLED | REJECTED | WITHDRAWN`, settlementStatus `NOT_APPLICABLE | PENDING_ADMIN_DECISION | SETTLED`, settlement columns (settledAt/By, reason, heldBefore, refundToClient, releaseToProvider, platformCommission, providerNet). DB rules: one PENDING-or-AGREED request per contract (partial unique index), requester must be a party (CHECK), `(requestedById, requestKey)` unique.

## Still open (not decided, nothing invented)
1. Project status after a settlement: there is no CANCELLED project status, so the dispute mapping is reused (COMPLETED when the provider is paid something, DISPUTED when nothing). Dashboards that count COMPLETED projects will count a cancelled-with-payment project; the derived "closed by settlement" label (`adminSettlementFor`) is still keyed on disputes only and is not extended to cancellations. Decide: add a CANCELLED project status / extend the derived label.
2. Expiry of a PENDING request, and whether a party may withdraw after agreement (today: no, only the administration can settle).
3. Whether an agreed cancellation with nothing left in escrow should be closable without money (today refused: nothing held).
4. Opening a request during an open dispute is refused (409); agreeing or settling during one is refused (423).
