# Baseline for a NEW, EMPTY database (ARB UAT environment)

**Scope.** This is for building one new database from nothing. It does not touch, replace or rewrite anything in `prisma/migrations/` (the shared history is unchanged), and it must never be run against an existing database (`apply.sh` refuses if the database has any table).

## Why a baseline is needed (the cause, not a workaround)

`prisma migrate deploy` on an empty database stops at the 20th migration:

```
Applying migration `20260828150000_harden_contract_acceptance_workflow`
ERROR: type "ContractStatus" does not exist
```

`ContractStatus` is altered by that migration (`ALTER TYPE "ContractStatus" ADD VALUE …`) but **no migration in the history ever creates it** (`grep 'CREATE TYPE "ContractStatus"'` finds nothing). The type was created outside the history (schema push) on the databases that exist today. So the history cannot be replayed from zero; this is a defect of the history that predates ARB and is not changed here.

## What the baseline is made of

| file | content | how it was made |
|---|---|---|
| `10-schema.generated.sql` | every table, enum, index, FK of `schema.prisma` at this commit (84 tables) | `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` |
| `20-non-prisma.sql` | the objects Prisma's DDL does not contain: partial unique index `ux_arb_payments_one_open_per_user`, CHECK `arb_payments_applied_consistent` | copied verbatim from the ARB migration |
| `30-reference-data.sql` | the only data the history inserts into an empty database (coupon `WASEET10`) | from `20260901120000_add_cart_checkout`; drop the file from `apply.sh` if the environment must not carry it |

Inventory of everything in the 50 migrations that is not plain table/enum/index DDL (checked by grep over all `migration.sql`): `ALTER TYPE … ADD VALUE` (enum values — present in `schema.prisma`, so in file 10), data `UPDATE`/`INSERT … SELECT` backfills of existing rows (nothing to backfill in an empty database), the coupon insert (file 30), the ARB partial index and CHECK (file 20). No extensions, functions, triggers, views or `COMMENT`s exist in the history. `payout_attempts.active_attempt_unique` (partial) is generated by Prisma itself (`partialIndexes` preview feature).

## Run order (`apply.sh`)

1. refuse unless the database is empty;
2. files 10, 20, 30 in ONE transaction (`ON_ERROR_STOP`, `--single-transaction`): all or nothing;
3. record the history. Registering the 50 folders as applied (`prisma migrate resolve --applied`, the documented Prisma baselining procedure) is correct **only because** step 2 produces, by construction, the schema those migrations lead to at this commit, and it is the only way `prisma migrate deploy` can later apply *new* migrations on top (otherwise it would try to replay the 50 and fail at the 20th). The claim "step 2 equals the history's result" is checked, not assumed: see Verification.

## Verification (what was run; results in the ARB report)

* empty database → `apply.sh` → `prisma migrate status` = up to date;
* `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma` = only the ARB partial index and CHECK (the two objects Prisma cannot read back; file 20);
* the same schema compared with a schema-only restore of the existing bank backup plus the reviewed upgrade SQL (`bank-upgrade-REVIEW.sql`): no differences other than the known partial objects;
* a probe migration (not in the repository, in a temporary copy of the migrations folder) applied with `prisma migrate deploy` on top of the baseline database, then the application booted and queried the new column;
* the application boots on the empty database (health check) with `ARB_ENABLED=false`.

## When this baseline is stale

If `schema.prisma` changes, regenerate file 10 and repeat the verification. Once the migration history is repaired (a migration that creates `ContractStatus`), this baseline is no longer needed.
